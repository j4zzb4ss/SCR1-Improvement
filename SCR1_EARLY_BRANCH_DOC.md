# Документация по добавленному макросу для процессора SCR1

## `SCR1_EARLY_BRANCH`

При включении макроса `SCR1_EARLY_BRANCH` в файле `scr1_arch_description.svh`
мы переносим раннее вычисление условного ветвления с исполнительного блока EXU
на более раннюю стадию IDU.

При этом EXU не перестаёт обрабатывать branch полностью. Он сохраняет повторную проверку
условия перехода и используется для correction redirect в случае, если ранний результат,
полученный в IDU, оказался некорректным.

Все изменения кода, относящиеся к данной оптимизации, защищены макросом `SCR1_EARLY_BRANCH`.

За счёт более раннего вычисления условия и target адреса мы сокращаем штраф за условный
переход. В максимальной конфигурации процессора в симуляции Verilator получили выигрыш
в CoreMark около **4.7%**.

В связке с L1 cache данное улучшение также даёт прирост на FPGA.
При одинаковой конфигурации кэша CoreMark показал увеличение производительности
по итерациям в секунду на **5.14%** при включённом раннем ветвлении.

Таким образом, раннее ветвление даёт дополнительный прирост производительности уже поверх
оптимизированной подсистемы памяти, при сравнительно небольшом объёме дополнительной логики.

---

## Схема обработки ветвлений

```text
                         ┌───────────────┐
                         │     MPRF      │
                         │               │
                         │ rs1 / rs2     │
                         │ + bypass      │
                         └──────┬────────┘
                                │
                                ▼
┌──────────┐  instr + PC  ┌──────────┐  early result  ┌──────────┐
│   IFU    │─────────────►│   IDU    │───────────────►│   EXU    │
│          │◄─────────────│          │                │ verifies │
└──────────┘ taken,target └──────────┘                └────┬─────┘
     ▲                                                     │
     │                 only on mismatch                    │
     └──────────── correction redirect ◄───────────────────┘
```

Основная идея состоит в том, что IDU получает операнды branch-инструкции раньше EXU,
вычисляет условие перехода и target адрес и при taken branch сразу перенаправляет IFU.

EXU позднее независимо вычисляет фактический результат ветвления и сравнивает его с тем,
что было получено в IDU.

Если результат совпал, повторный redirect не создаётся.

Если результат не совпал, EXU выполняет correction redirect и восстанавливает правильный
поток исполнения.

## 1) `scr1_riscv_isa_decoding.svh`

В структуру `type_scr1_exu_cmd_s` добавлены дополнительные поля:

```systemverilog
`ifdef SCR1_EARLY_BRANCH
logic early_branch_valid;
logic early_branch_taken;
`endif
```

`early_branch_valid` означает, что для данной branch-инструкции IDU действительно выполнил
раннее вычисление и передаваемый результат можно использовать для дальнейшей проверки.

`early_branch_taken` содержит сам результат раннего вычисления условия перехода.

Эти поля передаются вместе с командой из IDU в EXU.

## 2) `scr1_pipe_mprf.sv`

Для вычисления branch condition в IDU необходимо получить актуальные значения регистров
`rs1` и `rs2`.

Для этого добавлены новые порты чтения:

```text
idu2mprf_rs1_addr_i
mprf2idu_rs1_data_o

idu2mprf_rs2_addr_i
mprf2idu_rs2_data_o
```

Также организован bypass на случай, если EXU в текущий момент записывает значение в тот же
регистр, который требуется IDU.

В таком случае IDU получает значение напрямую из writeback path, не дожидаясь физического
обновления MPRF.

Это позволяет избежать ситуации, когда для вычисления branch condition используется
устаревшее значение регистра.

> **ВНИМАНИЕ:** текущая реализация рассчитана на конфигурацию
> `SCR1_MPRF_RAM = disabled`.
>
> При использовании RAM-реализации MPRF чтение может становиться синхронным, поэтому текущая
> схема раннего получения `rs1` и `rs2` требует отдельной адаптации.

## 3) `scr1_pipe_idu.sv`

При включённом `SCR1_EARLY_BRANCH` в IDU появляется дополнительный комбинационный тракт
для обработки условных переходов.

IDU:

- получает PC декодируемой инструкции;
- получает актуальные значения `rs1` и `rs2`;
- определяет тип условного перехода;
- вычисляет branch condition;
- вычисляет branch target;
- при taken branch формирует запрос на ранний redirect IFU.

Раннее ветвление обрабатывается только в момент успешного рукопожатия между IFU, IDU и EXU:

```systemverilog
assign idu_accept =
      ifu2idu_vd_i
    & exu2idu_rdy_i;
```

После этого дополнительно проверяется:

```systemverilog
if (idu_accept
    && ~ifu2idu_imem_err_i
    && ~idu2exu_cmd_o.exc_req
    && idu2exu_cmd_o.branch_req)
```

Это означает:

- IFU передал valid-инструкцию;
- EXU готов её принять;
- отсутствует ошибка чтения инструкции;
- декодирование не сформировало exception;
- инструкция является условной ветвью.

Target адрес вычисляется относительно PC самой branch-инструкции:

```text
branch_target = branch_pc + sign_extended_immediate
```

После вычисления результата информация сохраняется в команде для EXU:

```systemverilog
idu2exu_cmd_o.early_branch_valid = 1'b1;
idu2exu_cmd_o.early_branch_taken = branch_taken_early;
```

Если условие перехода выполнено, IDU одновременно передаёт IFU ранний запрос на изменение PC.

## 4) `scr1_pipe_ifu.sv`

В IFU были добавлены новые порты и внутренняя логика:

```text
idu2ifu_branch_req_i
idu2ifu_branch_target_i

ifu2idu_pc_o

ifu_idu_pc_ff
ifu_idu_instr_size
ifu_idu_accept

pc_new_req_internal
pc_new_addr_internal
```

Главная задача изменений — связать конкретную инструкцию, которую IFU выдаёт в IDU,
с её правильным PC.

Для этого добавлен отдельный контроль PC инструкции, передаваемой из IFU в IDU.

Это необходимо, потому что внутри IFU существует очередь инструкций и нельзя просто использовать
текущий fetch PC как PC декодируемой инструкции.

### Такт N

```text
IFU выдаёт branch-инструкцию и её PC в IDU.

IDU получает rs1 и rs2 из MPRF.

IDU вычисляет branch condition и branch target.
```

### Такт N, combinational

При taken branch:

```text
branch_taken_early = 1

idu2ifu_branch_req = 1

idu2ifu_branch_target =
    branch_pc + immediate
```

### Следующий фронт

IFU:

```text
очищает неправильный последовательный поток;

устанавливает fetch PC = branch target;

начинает запрос инструкции с нового адреса.
```

Сама branch-инструкция при этом передаётся дальше в EXU вместе с:

```text
early_branch_valid = 1
early_branch_taken = 1
```

При redirect также сохраняется штатный механизм отбрасывания старых instruction-memory responses,
которые могли быть запрошены до изменения PC.

Это необходимо для корректной работы при наличии незавершённых запросов instruction memory.

## 5) `scr1_pipe_exu.sv`

EXU сохраняет обычное вычисление результата branch.

Когда branch доходит до EXU, он повторно вычисляет условие перехода и получает фактический
результат:

```text
actual_branch_taken
```

После этого он сравнивается с результатом, который ранее вычислил IDU.

### Если результат совпал

```text
actual taken == early taken
```

ошибки нет.

Повторный redirect в IFU не создаётся.

Для корректно предсказанной taken branch IFU уже начал fetching с нужного target адреса,
поэтому дополнительное перенаправление только создало бы лишний штраф.

Внутреннее состояние EXU обновляется в соответствии с фактическим результатом branch.

### Если результат не совпал

```text
actual taken != early taken
```

формируется:

```text
early_branch_mispredict
```

и EXU отправляет correction redirect в IFU.

IFU очищает неправильный поток и начинает fetching с фактически правильного PC.

Таким образом, ранний результат IDU используется для ускорения нормального случая,
а EXU остаётся контрольной точкой, которая гарантирует корректность исполнения.

## 6) `scr1_pipe_top.sv`

В `scr1_pipe_top.sv` были добавлены соединения между:

```text
IFU
IDU
MPRF
EXU
```

для передачи:

```text
PC декодируемой инструкции;

rs1 / rs2 для раннего вычисления;

early branch request;

early branch target;

early_branch_valid;

early_branch_taken.
```

Сам `scr1_pipe_top.sv` не выполняет вычисление ветвления, но связывает между собой все блоки,
которые участвуют в новой схеме.

## Итоговая последовательность работы

Для корректно рано определённого taken branch:

```text
IFU
  ↓
IDU получает инструкцию + PC
  ↓
IDU получает rs1 / rs2 из MPRF
  ↓
IDU вычисляет condition и target
  ↓
IDU сразу перенаправляет IFU
  ↓
IFU начинает fetch с target
  ↓
branch позже доходит до EXU
  ↓
EXU повторно проверяет condition
  ↓
результат совпадает
  ↓
повторный redirect отсутствует
```

Для ошибочного раннего решения:

```text
IDU выполняет early redirect
  ↓
branch приходит в EXU
  ↓
EXU вычисляет фактический результат
  ↓
обнаруживается mismatch
  ↓
EXU выполняет correction redirect
  ↓
IFU очищает неправильный поток
  ↓
исполнение продолжается с правильного PC
```

## Производительность

Полученные результаты:

```text
Verilator CoreMark:
SCR1_EARLY_BRANCH ≈ +4.7%
```

На FPGA в конфигурации с L1 cache:

```text
L1 cache без pipeline / early branch:
CoreMark = 34.11 iter/s

L1 cache + pipeline / early branch:
CoreMark = 35.86 iter/s
```

Прирост:

```text
≈ +5.14% CoreMark
```

То есть раннее разрешение ветвлений даёт дополнительный прирост производительности
даже поверх уже оптимизированной подсистемы памяти.

При этом данная оптимизация не требует изменения ISA и полностью отключается
при отсутствии макроса `SCR1_EARLY_BRANCH`.
