# Документация по добавленному макросу для процессора SCR1

## SCR1_MEM_STAGE_EN

При включении макроса `SCR1_MEM_STAGE_EN` в конвейер процессора SCR1 добавляется дополнительная стадия MEM для обработки операций доступа к памяти.

В исходной реализации SCR1 операции load/store после EXU непосредственно взаимодействуют с LSU. В модифицированной реализации между EXU и LSU добавляется регистрируемая стадия MEM.

Основная цель изменения — разделить длинный комбинационный тракт между исполнительной частью процессора и подсистемой памяти, а также создать возможность перекрытия выполнения memory-инструкции с последующими простыми ALU-инструкциями.

Для этого дополнительно используется однозаписный WB-буфер, который позволяет сохранить результат младшей ALU-инструкции и освободить EXU, пока более старая memory-инструкция ещё находится в MEM.

Все изменения, относящиеся к данной модификации конвейера, защищены макросом:

```systemverilog
SCR1_MEM_STAGE_EN
```

При отключённом макросе сохраняется исходная организация конвейера SCR1.

---

# Изменение структуры конвейера

Упрощённо исходный путь выполнения memory-инструкции выглядел следующим образом:

```text
IFU
 ↓
IDU
 ↓
EXU
 ↓
LSU
 ↓
Data Memory
```

После включения `SCR1_MEM_STAGE_EN` между EXU и LSU появляется дополнительная стадия:

```text
IFU
 ↓
IDU
 ↓
EXU
 ↓
MEM
 ↓
LSU
 ↓
Data Memory
```

Одновременно для младших простых ALU-инструкций используется дополнительный WB-буфер:

```text
                    ┌──────────┐
                    │   MEM    │
                    │ memory op│
                    └────┬─────┘
                         │
                         ▼
                       LSU
                         │
                         ▼
                       MPRF

IFU → IDU → EXU
              │
              └──────────────► WB
                                │
                                ▼
                               MPRF
```

Таким образом, в определённых ситуациях одновременно могут находиться три разные инструкции:

```text
MEM : instruction N
WB  : instruction N+1
EXU : instruction N+2
```

Например:

```text
MEM : LOAD x5, 0(x1)
WB  : ADD  x6, x2, x3
EXU : следующая инструкция
```

Это позволяет уменьшить блокировку EXU во время выполнения операции доступа к памяти.

---

# Назначение MEM-stage

MEM-stage используется для хранения информации о более старой memory-инструкции после того, как EXU уже вычислил необходимые значения.

При передаче инструкции из EXU в MEM сохраняются:

```text
тип LSU-команды;
адрес memory access;
данные STORE;
адрес регистра назначения rd;
признак записи rd;
PC инструкции;
состояние valid/request.
```

Основные сигналы интерфейса EXU → MEM:

```systemverilog
exu2mem_req_o
exu2mem_lsu_cmd_o
exu2mem_addr_o
exu2mem_sdata_o
exu2mem_rd_addr_o
exu2mem_pc_o
exu2mem_rd_w_req_o
```

Обратный интерфейс MEM → EXU используется для передачи состояния и результата завершившейся memory-операции:

```systemverilog
mem2exu_rdy_i
mem2exu_done_i
mem2exu_ldata_i
mem2exu_exc_i
mem2exu_exc_code_i
mem2exu_rd_addr_i
mem2exu_rd_w_req_i
mem2exu_pc_i
mem2exu_addr_i
```

---

# Передача инструкции EXU → MEM

Memory-инструкция считается принятой MEM при выполнении:

```systemverilog
mem_accept =
      lsu_req
    & mem2exu_rdy_i;
```

После успешной передачи EXU может освободиться для следующей инструкции.

Состояние занятой MEM-stage определяется через готовность MEM принять новую операцию.

Условно:

```text
EXU вычисляет адрес LOAD/STORE
          ↓
MEM готов
          ↓
операция фиксируется в MEM registers
          ↓
EXU может перейти к следующей инструкции
```

Адрес memory access формируется в EXU:

```systemverilog
exu2mem_addr_o = ialu_addr_res;
```

Для STORE также сохраняются данные второго операнда:

```systemverilog
exu2mem_sdata_o = mprf2exu_rs2_data_i;
```

---

# WB-буфер

Одного добавления MEM-stage недостаточно для полного освобождения EXU.

Рассмотрим последовательность:

```text
LOAD x5, 0(x1)
ADD  x6, x2, x3
```

После передачи LOAD в MEM инструкция ADD может быть вычислена в EXU.

Однако если более старая LOAD ещё не завершена, результат ADD нельзя безусловно записывать в архитектурное состояние раньше неё.

Если результат ADD негде сохранить, инструкция должна оставаться в EXU и блокировать следующую инструкцию.

Для решения этой проблемы добавлен однозаписный WB-буфер.

Добавлены регистры:

```systemverilog
logic                         wb_vd_ff;
logic [`SCR1_MPRF_AWIDTH-1:0] wb_rd_addr_ff;
logic [`SCR1_XLEN-1:0]        wb_rd_data_ff;
logic [`SCR1_XLEN-1:0]        wb_pc_ff;
```

Они хранят:

```text
valid результата;
адрес регистра назначения;
данные для записи;
PC инструкции.
```

В результате последовательность может выполняться следующим образом:

```text
Такт N:

MEM : LOAD
EXU : ADD

       ↓

результат ADD сохраняется в WB

Такт N+1:

MEM : LOAD
WB  : ADD
EXU : следующая инструкция
```

Таким образом, основная цель WB — не только арбитраж записи в MPRF, а возможность физически освободить EXU до завершения более старой memory-инструкции.

---

# Какие инструкции допускаются в WB

В WB разрешается помещать только инструкции без побочных эффектов, результат которых уже полностью вычислен в EXU.

Используется условие `wb_bufferable`.

В текущей реализации поддерживаются результаты:

```systemverilog
SCR1_RD_WB_IALU
SCR1_RD_WB_SUM2
SCR1_RD_WB_IMM
```

При этом в WB не помещаются инструкции:

```text
LOAD / STORE;
CSR;
branch;
jump;
MRET;
FENCE.I;
WFI;
exception;
```

Также учитываются RAW-зависимости от незавершённой memory-инструкции и уже занятого WB.

Это необходимо для сохранения корректного порядка выполнения.

---

# Формирование данных WB

Данные для WB формируются непосредственно из результатов EXU:

```systemverilog
case (exu_queue.rd_wb_sel)

    SCR1_RD_WB_SUM2:
        wb_push_data = ialu_addr_res;

    SCR1_RD_WB_IMM:
        wb_push_data = exu_queue.imm;

    default:
        wb_push_data = ialu_main_res;

endcase
```

Важно, что данные берутся непосредственно из соответствующего результата EXU.

Они не захватываются из общего `exu2mprf_rd_data_o`, поскольку данный путь также используется для завершившегося LOAD и имеет собственный приоритет.

---

# Передача EXU → WB

Запись результата в WB выполняется при условии:

```systemverilog
assign wb_push =
       mem_pending
     & wb_bufferable
     & exu_rdy
     & ~wb_vd_ff;
```

То есть:

```text
MEM содержит незавершённую старшую инструкцию;
текущая EXU-инструкция допускает буферизацию;
EXU завершил вычисление;
WB свободен.
```

После `wb_push` результат сохраняется:

```systemverilog
wb_vd_ff      <= 1'b1;
wb_rd_addr_ff <= exu_queue.rd_addr;
wb_rd_data_ff <= wb_push_data;
wb_pc_ff      <= pc_curr_ff;
```

С этого момента младшая ALU-инструкция больше не занимает EXU.

---

# Арбитраж единственного порта записи MPRF

В SCR1 используется один основной порт записи MPRF.

После добавления MEM и WB потенциально существует несколько источников записи:

```text
LOAD completion из MEM;
результат из WB;
обычная инструкция из EXU.
```

Поэтому введён фиксированный приоритет:

```text
1. завершившийся LOAD;
2. WB;
3. обычный EXU writeback.
```

Адрес регистра назначения выбирается следующим образом:

```systemverilog
assign exu2mprf_rd_addr_o =
    load_wb_req
        ? mem2exu_rd_addr_i
        : wb_commit
            ? wb_rd_addr_ff
            : exu_queue.rd_addr;
```

А данные:

```text
LOAD result
    ↓
WB result
    ↓
EXU result
```

Более старая memory-инструкция имеет приоритет перед более молодой инструкцией из WB.

Это необходимо для сохранения порядка архитектурных изменений состояния.

---

# RAW hazard для незавершённого LOAD

После добавления MEM инструкция LOAD может находиться в MEM, в то время как следующая инструкция уже находится в EXU.

Например:

```text
LOAD x5, 0(x1)
ADD  x6, x5, x2
```

ADD не может выполняться до получения значения `x5`.

Для этого добавлена проверка `load_raw_hazard`.

Проверяется:

```text
MEM занята;
memory-инструкция выполняет запись rd;
rd != x0;
следующая инструкция использует rs1 или rs2;
rs1/rs2 совпадает с rd незавершённого LOAD.
```

При обнаружении такой зависимости младшая инструкция блокируется до получения корректного значения.

---

# RAW hazard для WB

Аналогично контролируется зависимость от инструкции, находящейся в WB.

Например:

```text
ADD x5, x1, x2
SUB x6, x5, x3
```

Если ADD временно находится в WB, следующая инструкция не должна использовать устаревшее значение `x5`.

Для этого добавлен сигнал:

```systemverilog
wb_raw_hazard
```

Он сравнивает `wb_rd_addr_ff` с используемыми `rs1` и `rs2` текущей инструкции.

---

# Сохранение порядка выполнения

MEM содержит более старую инструкцию, чем WB и EXU.

Поэтому младшие инструкции не должны выполнять необратимые side effects раньше старшей memory-инструкции.

Для этого используется блокировка:

```systemverilog
assign exu_order_block =
       mem_pending
     | wb_vd_ff;
```

Пока существует незавершённая старшая операция, ограничивается выполнение младших операций, влияющих на архитектурное состояние.

Это особенно важно для:

```text
новых memory operations;
CSR;
exceptions;
MRET;
WFI;
FENCE.I;
branch/jump redirect;
interrupt handling.
```

---

# Precise exceptions

После добавления MEM memory exception может возникнуть позже, когда в EXU или WB уже находится более молодая инструкция.

Необходимо гарантировать precise exception semantics.

Пример:

```text
LOAD x5, 0(x1)     ← старшая
ADD  x6, x2, x3    ← младшая
```

В момент обнаружения access fault возможна ситуация:

```text
MEM : LOAD
WB  : ADD
```

Если LOAD получает exception, результат ADD не должен попасть в архитектурное состояние.

Поэтому memory exception имеет приоритет.

При обнаружении:

```systemverilog
mem2exu_exc_i
```

WB очищается:

```systemverilog
if (mem2exu_exc_i) begin
    wb_vd_ff <= 1'b0;
end
```

То есть младший результат уничтожается.

---

# PC и адрес exception

Поскольку memory-инструкция уже покинула EXU, её PC необходимо сохранить в MEM.

Для этого используется:

```systemverilog
exu2mem_pc_o
mem2exu_pc_i
```

При exception текущим PC для trap logic становится PC именно memory-инструкции:

```systemverilog
assign exu2pipe_pc_curr_o =
    lsu_exc_req
        ? mem2exu_pc_i
        : pc_curr_ff;
```

Для load/store fault также сохраняется фактический адрес memory access:

```systemverilog
mem2exu_addr_i
```

Он используется для формирования соответствующего `mtval`.

Таким образом, даже если EXU уже обрабатывает другую инструкцию, exception содержит PC и адрес именно той memory-инструкции, которая вызвала fault.

---

# Продвижение PC

После введения WB важно правильно определить момент, когда инструкция фактически покинула EXU.

Для memory-инструкции это происходит при:

```text
mem_accept
```

Для локально завершившейся инструкции:

```text
exu_local_retire
```

Для инструкции, переданной в WB:

```text
wb_push
```

Поэтому продвижение PC связано именно с передачей инструкции из EXU в следующую точку хранения, а не с более поздним `wb_commit`.

Используется:

```systemverilog
assign exu_pc_advance =
       mem_accept
     | exu_local_retire
     | wb_push;
```

Это принципиально важно.

После `wb_push` инструкция уже не принадлежит EXU, поэтому EXU должен перейти к PC следующей инструкции.

---

# Завершение WB

Инструкция из WB может быть записана в MPRF только после того, как более старая memory-инструкция больше не блокирует commit.

Условие:

```systemverilog
assign wb_commit =
       wb_vd_ff
     & ~mem_pending;
```

После `wb_commit`:

```text
WB result → MPRF
```

и:

```systemverilog
wb_vd_ff <= 1'b0;
```

После этого WB снова может принять новый результат.

---

# Последовательность работы

Рассмотрим:

```text
LOAD x5, 0(x1)
ADD  x6, x2, x3
SUB  x7, x8, x9
```

Работа может происходить следующим образом.

```text
Такт N

EXU:
LOAD вычисляет адрес

        ↓

LOAD передаётся в MEM
```

Далее:

```text
Такт N+1

MEM:
LOAD ожидает LSU / memory

EXU:
ADD вычисляет результат
```

При занятой MEM:

```text
ADD → WB
```

После этого:

```text
Такт N+2

MEM : LOAD
WB  : ADD
EXU : SUB
```

Таким образом, EXU не обязан ждать завершения LOAD для начала обработки независимых инструкций.

Когда LOAD завершается:

```text
LOAD result → MPRF
```

После освобождения старшей операции:

```text
ADD result из WB → MPRF
```

---

# Случай зависимости от LOAD

Для последовательности:

```text
LOAD x5, 0(x1)
ADD  x6, x5, x3
```

работа отличается:

```text
MEM:
LOAD x5

EXU:
ADD требует x5
```

Обнаруживается:

```text
load_raw_hazard = 1
```

и ADD не продвигается до момента завершения LOAD.

После записи актуального значения `x5` выполнение может продолжиться.

То есть overlap разрешается только для действительно независимых инструкций.

---

# Случай exception

Для:

```text
LOAD x5, invalid_address
ADD  x6, x2, x3
```

возможна ситуация:

```text
MEM : LOAD
WB  : ADD
```

Если LOAD вызывает exception:

```text
MEM exception
     ↓
WB invalidated
     ↓
ADD не записывается в MPRF
     ↓
trap использует PC LOAD
     ↓
mtval получает faulting address
```

Таким образом сохраняются precise exceptions.

| Название файла | Правки | Зачем нужно |
|---|---|---|
| `scr1_arch_description.svh` | Добавлен/включается `SCR1_MEM_STAGE_EN` | Управление включением новой стадии |
| `scr1_pipe_mem.sv` | Добавлена новая MEM-stage | Хранение и выполнение старшей memory-инструкции вне EXU |
| `scr1_pipe_exu.sv` | Добавлены интерфейс MEM, WB-буфер, hazard/ordering logic, MPRF arbitration | Освобождение EXU и корректная работа нового pipeline |

| `scr1_pipe_lsu.sv` / связанная LSU-логика | Адаптация интерфейса к MEM-stage | Выполнение memory operation после новой регистровой границы |

---

# 1) scr1_pipe_mem.sv

Добавлен новый модуль:

```systemverilog
scr1_pipe_mem
```

Он размещается логически между EXU и LSU.

Основная задача MEM-stage — принять сформированную в EXU memory-операцию и удерживать её состояние до завершения доступа к памяти.

MEM хранит:

```text
LSU command;
address;
store data;
rd;
rd write request;
PC.
```

Для LOAD после завершения LSU обратно передаются:

```text
loaded data;
rd;
PC;
exception status;
exception code;
faulting address.
```

---

# 2) scr1_pipe_exu.sv

В EXU добавлена основная управляющая логика новой схемы.

Добавлены:

```text
EXU → MEM interface;
MEM → EXU completion interface;
WB buffer;
load RAW detection;
WB RAW detection;
ordering control;
MPRF write arbitration;
precise exception handling.
```

Memory-инструкция после вычисления адреса больше не обязана оставаться владельцем EXU до окончания LSU transaction.

При успешном `mem_accept` она передаётся в MEM.

Для независимой младшей ALU-инструкции при занятой MEM результат может быть помещён в WB через `wb_push`.

---

# 3) scr1_pipe_top.sv

В `scr1_pipe_top.sv` добавлен экземпляр:

```systemverilog
i_pipe_mem
```

и соединения:

```text
EXU → MEM
MEM → EXU
MEM → LSU
LSU → MEM
```

`pipe_top` не выполняет самостоятельных вычислений новой стадии, а связывает все участвующие блоки.

---

# Архитектурный эффект

Добавление MEM-stage создаёт дополнительную регистровую границу в memory datapath.

Исходно длинный путь проходил через комбинационную логику EXU/LSU и далее в подсистему памяти.

После введения новой стадии memory operation фиксируется раньше:

```text
EXU
 ↓
MEM register boundary
 ↓
LSU
```

Это позволяет отделить часть memory path от EXU и потенциально увеличить максимально допустимую частоту процессора.

Одновременно WB позволяет использовать новую стадию не только как дополнительную задержку memory operation, но и для реального перекрытия исполнения независимых инструкций.

---

# Производительность

В функциональной симуляции CoreMark новая схема с реальным overlap показала уменьшение числа циклов относительно более консервативного варианта:

```text
5436 cycles
→
5404 cycles
```

Выигрыш непосредственно от overlap составляет примерно:

```text
32 cycles
≈ 0.59%
```

При этом основная цель MEM-stage заключается не только в уменьшении CPI, но и в изменении критического пути и создании возможности повышения тактовой частоты.

---

# Timing analysis

Post-route timing analysis показал, что после добавления MEM-stage исходный критический путь через memory/LSU subsystem перестал быть самым длинным.

Это означает, что новая регистровая граница действительно изменила критический тракт процессора.

Однако после данной модификации проявился новый критический путь во внутренней управляющей логике:

```text
EXU
 ↓
WB / MPRF-related logic
 ↓
EARLY_BRANCH
 ↓
HDU
 ↓
IFU
 ↓
instruction-memory address register
```

Поэтому текущая реализация требует дополнительной timing-оптимизации этого тракта.

При этом задача дальнейшей оптимизации состоит в том, чтобы сохранить работу `SCR1_EARLY_BRANCH` и его уменьшенный branch penalty, но удалить лишнюю комбинационную зависимость между новой MEM/WB-логикой и трактом раннего redirect.

---

# Совместная работа с SCR1_EARLY_BRANCH

Макросы:

```systemverilog
SCR1_MEM_STAGE_EN
SCR1_EARLY_BRANCH
```

могут использоваться одновременно.

При этом:

```text
SCR1_MEM_STAGE_EN
```

оптимизирует организацию memory path и допускает overlap независимых инструкций,

а:

```text
SCR1_EARLY_BRANCH
```

уменьшает штраф условных переходов за счёт более раннего вычисления branch condition и target.

Эти механизмы решают разные задачи и дополняют друг друга.

Важно, чтобы дальнейшая timing-оптимизация MEM/WB-path не добавляла дополнительный регистр в тракт:

```text
IDU → early branch → IFU
```

поскольку это снова увеличило бы branch penalty.

# Итог

При включённом `SCR1_MEM_STAGE_EN`:

```text
memory operation
```

переносится из EXU в отдельную MEM-stage;

```text
independent ALU operation
```

может быть временно сохранена в WB;

```text
EXU
```

может раньше принять следующую инструкцию;

RAW-зависимости блокируются;

единственный write-port MPRF получает фиксированный arbitration priority;

исключения от более старой memory-инструкции сохраняют precise semantics;

PC и faulting address сохраняются вместе с memory operation;

ISA процессора не изменяется.

Таким образом, `SCR1_MEM_STAGE_EN` является микроархитектурной оптимизацией, которая добавляет регистровую границу в memory path и создаёт возможность перекрытия выполнения memory-инструкций с независимыми вычислительными инструкциями.

Текущая реализация функционально проходит CoreMark и является основой для дальнейшего повышения Fmax за счёт оптимизации нового критического пути EXU–IDU–IFU.
