# Critical Paths Optimization

Оптимизация критических путей SCR1 выполнялась по результатам post-route timing analysis. Основная идея заключалась не в добавлении отдельной функциональной возможности, а в последовательном разрыве длинных комбинационных трактов, ограничивающих максимальную рабочую частоту процессора.

В ходе работы критический путь несколько раз менялся: после устранения одного длинного тракта наиболее критичным становился следующий.

Основные изменения выполнялись совместно с оптимизациями `SCR1_MEM_STAGE_EN` и `SCR1_EARLY_BRANCH`.

## Исходный критический путь

После переноса обработки условных переходов из EXU в IDU с помощью `SCR1_EARLY_BRANCH` раннее решение branch первоначально использовало bypass результатов из EXU.

Схема имела вид:

```text
EXU / IALU
    ↓
MPRF bypass
    ↓
IDU branch comparator
    ↓
IDU redirect logic
    ↓
IFU next-PC logic
    ↓
instruction memory interface
```

Такой вариант обеспечивал IDU наиболее актуальными значениями `rs1` и `rs2`, однако создавал длинный комбинационный тракт практически через несколько стадий процессора.

Post-route анализ показал задержку порядка:

```text
32.438 ns
```

Таким образом уменьшение CPI за счёт раннего разрешения branch сопровождалось существенным ухудшением Fmax.

## Удаление EXU → IDU bypass

Для разрыва критического пути непосредственный forwarding результатов EXU в специальные операнды `EARLY_BRANCH` был удалён.

После изменения раннее сравнение использует только данные, уже находящиеся в MPRF:

```text
          MPRF
        ┌───┴───┐
        ↓       ↓
      rs1       rs2
        └───┬───┘
            ↓
           IDU
      EARLY_BRANCH
            ↓
           IFU
```

Из комбинационного пути исключается участок:

```text
EXU result
   ↓
bypass mux
   ↓
IDU branch comparator
```

В результате EXU перестаёт непосредственно участвовать в формировании раннего следующего PC.

## Проблема устаревших данных MPRF

Удаление bypass означает, что IDU в некоторых случаях может использовать ещё не обновлённое значение регистра.

Например:

```text
instruction N:
    ADD x5, ...

instruction N+1:
    BNE x5, x6, target
```

В момент декодирования branch новое значение `x5` может ещё находиться в EXU, MEM или WB и не быть записано в MPRF.

Поэтому результат `EARLY_BRANCH` используется как раннее решение, но не считается окончательным.

В IDU вместе с branch передаются:

```text
early_branch_valid
early_branch_taken
```

## Финальная проверка в EXU

EXU повторно вычисляет условие перехода по актуальным операндам:

```text
branch_taken
```

После чего сравнивает его с ранним результатом IDU:

```text
branch_taken != early_branch_taken
```

При несовпадении формируется:

```text
early_branch_mispredict
```

и EXU выполняет корректирующий redirect.

Для фактически taken branch:

```text
EXU → branch target
```

Для фактически not-taken branch:

```text
EXU → sequential PC
```

Получается двухуровневая схема:

```text
IDU EARLY_BRANCH
      ↓
быстрый speculative redirect
      ↓
EXU verification
      ↓
correction только при ошибке
```

В типичном случае EXU больше не участвует в формировании нового PC.

## Оптимизированный критический путь

До оптимизации:

```text
EXU
 ↓
IALU result
 ↓
forwarding / bypass mux
 ↓
IDU branch comparator
 ↓
IFU next-PC logic
 ↓
IMEM
```

После оптимизации:

```text
MPRF
 ↓
IDU branch comparator
 ↓
IFU next-PC logic
 ↓
IMEM
```

Это позволило уменьшить post-route задержку примерно с:

```text
32.438 ns
```

до:

```text
≈ 27.0–27.1 ns
```

Для сравнения классическая конфигурация SCR1 показывала значение около:

```text
26.77 ns
```

Таким образом после разрыва EXU → IDU bypass новый вариант приблизился по timing к исходному SCR1, сохранив преимущество раннего разрешения условных переходов.

## Взаимодействие с MEM-stage

После добавления `SCR1_MEM_STAGE_EN` часть результатов может находиться в:

```text
EXU
MEM
WB
```

Попытка организовать полный forwarding всех этих результатов непосредственно в ранний branch comparator снова привела бы к длинному тракту:

```text
EXU / MEM / WB
      ↓
forwarding muxes
      ↓
IDU EARLY_BRANCH
      ↓
IFU next PC
```

Поэтому была сохранена более короткая схема:

```text
MPRF
 ↓
IDU
 ↓
IFU
```

а проверка корректности вынесена в более позднюю стадию:

```text
EXU
 ↓
IFU correction
```

Такой подход позволяет не включать сеть forwarding из EXU/MEM/WB в критический путь формирования PC.

## Последовательность оптимизации путей

Работа выполнялась итеративно.

Изначально одним из критических являлся тракт через memory subsystem:

```text
EXU
 ↓
LSU
 ↓
memory interface
```

Добавление отдельной MEM-stage разорвало этот путь:

```text
EXU
 ↓
MEM registers
 ↓
LSU
```

После этого timing analysis выявил новый критический тракт, связанный с ранним branch:

```text
EXU / WB
 ↓
forwarding
 ↓
EARLY_BRANCH
 ↓
IFU
```

Следующим этапом был разрыв уже этого пути путём удаления EXU → IDU bypass.

Таким образом оптимизация выполнялась по принципу:

```text
найти critical path
        ↓
разорвать его регистрами
или убрать длинный forwarding
        ↓
повторить post-route analysis
        ↓
найти следующий critical path
```

## Результат

Оптимизация позволила одновременно сохранить выигрыш по CPI от `EARLY_BRANCH` и существенно сократить ухудшение timing.

Первая версия раннего branch давала примерно:

```text
≈ 4.7 % уменьшения числа циклов CoreMark
```

и порядка:

```text
≈ 170 cycles
```

экономии за счёт более раннего разрешения переходов.

При этом первоначальный критический путь составлял:

```text
32.438 ns
```

После удаления длинного bypass:

```text
≈ 27.0–27.1 ns
```

То есть основная идея `Critical Paths Optimization` состоит в замене длинных комбинационных зависимостей:

```text
EXU / MEM / WB
      ↓
несколько уровней forwarding
      ↓
управляющая логика
```

на более короткие пути с регистрацией промежуточных результатов и поздней коррекцией редких ошибочных ситуаций.

В результате процессор сохраняет функциональную корректность и уменьшенный CPI, одновременно получая более благоприятную структуру для повышения Fmax.
